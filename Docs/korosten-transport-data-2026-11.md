# Коростень, фаза 8 — чернетка датасету з джерел

**Статус:** зроблено 2026-11-12 (PR фази 8) · запис у прод — власник · **Мастер-план:**
[`korosten-transport-2026-11.md`](korosten-transport-2026-11.md) · **Звіт чернетки:**
[`data/korosten-transport/dataset/REPORT.md`](../data/korosten-transport/dataset/REPORT.md)

Генератор збирає з файлів у `data/korosten-transport/` датасет Коростеня у форматі `PUT /transport/dataset`
(зупинки з координатами, ланцюжки, варіанти шляху, рейси, сегменти, кольори) і звіт «що перевірити руками».
Мережі генератор не торкається; знімки зовнішніх джерел робляться окремими прапорцями і комітяться.

## Як запускати

```bash
cd backend && npm run build
npm run korosten:dataset                    # джерела → dataset/korosten-dataset.json + dataset/REPORT.md
npm run korosten:dataset -- --fetch-osm     # + знімок OSM (зупинки, маршрути) і вулиць (Nominatim), далі генерація
npm run korosten:dataset -- --fetch-streets # лише вулиці
npm run korosten:dataset -- --fetch-google  # + перевірка через Google (потрібен GOOGLE_MAPS_API_KEY)
npm run korosten:dataset -- --fetch-google --only-missing  # пошук Places лише для зупинок, яких ще нема в google/check.json
npm run korosten:dataset -- --fetch-google-coords  # координати Google за place_id (Place Details) → google/coords.local.json
npm run korosten:dataset -- --google-hops --google-coords  # перевірка кожного прогону A → B → C (Routes TRANSIT), продовжує з місця зупинки
npm run korosten:dataset -- --google-hops --refresh         # те саме з нуля
npm run korosten:dataset -- --google-coords # + dataset/korosten-dataset.local.json і REPORT.local.md з точками Google (поза git)
npm run korosten:dataset -- --dry-run       # порівняти з базою (ADMIN_TOKEN / VIBER_ADMIN_TOKEN), нічого не писати
npm run korosten:dataset -- --apply         # GET → бекап у ~/korosten-backups → PUT ?city=Korosten з baseRevision → GET і звірка
```

`API_BASE` — за замовчуванням адреса з `frontend/scripts/api-base.mjs`; `OVERPASS_URL` — список дзеркал через кому
(з хмарної сесії `overpass-api.de` недоступний, `maps.mail.ru/osm/tools/overpass` — так).

Другий шлях запису — адмінка: «Редактор карти» → місто «Коростень» → **«Імпорт датасету з файлу…»** → обрати
`data/korosten-transport/dataset/korosten-dataset.json` → підтвердити «зупинок A → B…». Кнопка є лише для не-Малина;
запит той самий (`PUT ?city=Korosten` з ревізією, `meta` бази лишається під `meta` файлу). Повторний запуск
`--apply` нічого не робить, якщо в базі вже ця чернетка.

**Імпорт замінює весь датасет міста.** Після ручних правок у редакторах (фаза 9) повторний імпорт їх зітре —
тоді джерелом стає база, а генератор лише підказує (`--dry-run`).

## Правила

Ручні рішення — в одному файлі `data/korosten-transport/dataset-config.json`; решта береться з джерел як є.

| Що | Звідки | Правило |
|---|---|---|
| Зупинки | `source/stops.csv` + нові з розкладу (`stop-aliases.json`) | `z-0NN` → `st_10NN`, `z-101…` → `st_1101…`; назва почищена: «Зупинка на вимогу «X»» → «X (на вимогу)», лапки «», пробіли. У датасет — лише зупинки з ланцюжків і варіантів |
| Координати | OSM → вулиця → сусіди → продовження | див. нижче; джерело кожної точки — у звіті |
| Маршрути | `dataset-config.json` + `routes.csv` | id `1`…`8`, `2b` («2-Б»); кінцеві — назви крайніх зупинок ланцюжка «туди»; опис ради в `note` |
| Ланцюжки | `project-2025/chains.json` | напрямок 1 → `orderThere`, 2 → `orderBack`. №2-Б — склеєний: №2 до вокзалу + №8 (Школа №1, Районна лікарня) до Романа Шухевича (опис ради й схема 2019) |
| Варіанти шляху | `dataset-config.json` | шматки напрямків проєкту + окремі зупинки; №2 до/від Романа Шухевича, №6 по Південній (курсив), №8 до Садів і до Дач УТОС |
| Сегменти | хвилини проєкту | різниця × 60 с, мінімум 30 с; невідомі перегони варіантів — медіана часу ради мінус відоме, порівну |
| Рейси | `source/timetable.json` (рада 2026) | див. нижче |
| Кольори | `scheme-2019/README.md` | `meta.routeColors` (номер на кольорі — `textColorOn()` на сайті) |

Перевізників (`agency.csv`) у чернетці нема: там телефони ФОП — не публікуємо без потреби.

### Координати

1. **OSM** — точка за назвою після нормалізації (`stopNameKeys`) або за підказкою `osmHints` (id точки → `z-0NN`,
   `null` — не брати). Кілька точок однієї зупинки → найбільша група в радіусі 200 м, середня точка; решта — у звіт.
2. **Вулиця** зі `stops.csv` через Nominatim (одна точка на вулицю). Якщо на вулиці кілька зупинок, точку отримує
   середня з них за порядком ланцюжка, решта — наступний крок (інакше купа в одній точці).
3. **Між сусідами** в ланцюжку — за хвилинами проєкту (або рівномірно).
4. **Продовження лінії** за останню відому точку, крок 300 м — для кінців без жодної відомої точки.

Без жодної точки генератор зупиняється з помилкою, а не вигадує. Звіт перелічує всі точки не з OSM і «підозрілі
перегони» (швидше 45 км/год) — це список для фази 9.

**Google** (`--fetch-google`: Places API Text Search з `includedType: bus_stop` у межах міста; Routes API TRANSIT між
кінцевими кожного маршруту). У репозиторій (`google/check.json`) — лише `place_id`, назва, відстань від нашої точки й
номери ліній, які пропонує Google: координати Google в публічний репозиторій не кладемо (умови Google Maps Platform).

**Координати Google тимчасово** (рішення власника 2026-11-12: відкриті формати Коростеня поки не публікуються, зупинки
власник об'їде сам): `--fetch-google-coords` бере їх за `place_id` у `google/coords.local.json`, `--google-coords` збирає
`dataset/korosten-dataset.local.json` + `REPORT.local.md` — усе в `.gitignore`. Цю версію імпортують кнопкою в адмінці
або `--google-coords --apply`. Точка Google замінює лише приблизну (не OSM) і лише якщо узгоджена з сусідами по
ланцюжку: до кожного сусіда з відомою точкою не далі max(1 км, 15 м/с × хвилини між ними); ідемо хвилями від точок OSM,
далі приймаються ланцюжки з ≥ 3 сусідніх узгоджених точок Google без якоря. Решта — у звіті «Google: точки, яких не
взяли» (однойменні зупинки деінде). Після об'їзду точки Google замінюються власними в «Редакторі карти».

Ключ: Places API читає його із заголовка `X-Goog-Api-Key`, захищена форма сесії вміє лише `Authorization: Bearer` —
ключ лежить у налаштуваннях середовища (Network secrets → `places.googleapis.com`, `routes.googleapis.com`, заголовок
`X-Goog-Api-Key`). Запуск у хмарі: `NODE_USE_ENV_PROXY=1 GOOGLE_MAPS_API_KEY=via-proxy npm run korosten:dataset -- …`
(вбудований `fetch` Node без `NODE_USE_ENV_PROXY` іде повз проксі, і ключ не підставляється). Квота пошуку — на день
(два прогони по 83 запити її вичерпали), Place Details — окрема; Routes ComputeRoutes — теж на день (≈ 100 запитів).

### Перевірка кожного прогону через Google (`--google-hops`, фаза 9 без поїздки)

На прохання власника: «перевір кожен прогін з зупинки один через другу до третьої, якраз повороти на карті».
`korosten-google.ts` (чисті функції) бере всі ланцюжки датасету (основні напрямки й варіанти, без технічних точок) і
трійки сусідніх зупинок A → B → C (спільна для кількох маршрутів — одна, ≈ 170 на місто). Для кожної — Routes TRANSIT
від A до C з альтернативами в будній день о першому рейсі цього ланцюжка після 07:00 (мінус 5 хв). Висновок:

- **ок** — Google пропонує наш номер одним кроком, `stopCount` = 2 (між A і C рівно одна зупинка), наші A, B, C не
  далі 80 м від траси Google, а прямі A→B і B→C відходять від неї не більше 150 м;
- **інша кількість перегонів** — Google не має нашої B або має свою зупинку між ними;
- **не на трасі** — наша точка далі 80 м від лінії шляху Google (не та точка або не та вулиця);
- **зрізає поворот** — тут поворот, на карті потрібні технічні точки (фаза 9);
- **інша лінія / нема транспорту** — Google не знає нашого маршруту тут або радить пішки.

Лінія шляху Google — лише для звірки. У git (`google/hops.json`) — висновки без координат Google: відстані, номери
ліній і `oursHash` (хеш наших координат A, B, C на момент перевірки). Звіт показує лише висновки, чиї `oursHash`
збігаються з поточними точками; інакше «на інших точках — перезапустити». Повні відповіді — `google/hops.local.json`
(поза git). Скрипт пише прогрес кожні 20 запитів і зупиняється на першій помилці (429 квоти); наступний запуск
продовжує. Звіт: розділ «Перевірка прогонів через Google» з таблицею проблемних трійок — план фази 9.

### Рейси

- Ланцюжок рейсу — основний напрямок, якщо кінцеві й проміжні пункти рядка ради лежать на ньому по порядку; інакше —
  варіант шляху з `dataset-config.json`; курсив — лише варіант з `when.italic`, рядок з приміткою — лише варіант,
  чий `when.note` входить у текст примітки («Франка»). Рядок з приміткою без такого варіанта і кінцеві поза
  ланцюжками — не пишемо, перелік у звіті. Серед кількох варіантів — основний, далі той, що починається з кінцевої
  рядка або нею закінчується.
- `sameStop` у конфігу — дві назви з розкладу ради, які є однією зупинкою («Коростень-Грозине» — назва напрямку,
  рейс іде від Грозиного). Тимчасові id (`st_1104`, `st_1105`) уже в базі, тому підказки псевдонімів не міняємо.
- `coordOverrides` — ручна точка (джерело «ручні» у звіті) лише з відкритих джерел або з поїздки, ніколи з Google;
  точка OSM важливіша.
- **Головна пара кінцевих.** Рада пише кінцеві грубо («Чигирі» там, де ланцюжок проєкту йде до Проліскової;
  «Романа Шухевича» там, де №8 починається від Магазину №44). Найчастіша пара основного ланцюжка означає весь
  ланцюжок; інші пари всередині нього — скорочені рейси (`startStopId` / `endStopId`).
- `serviceId`: рядок ради з «*» і приміткою «не виконуються в суботу та неділю» або з приміткою «крім суботи та
  неділі» → `weekdays`, решта — `everyday`.
  Окремих вихідних рейсів (календар `weekends`) ще нема — фаза 7; звіт перелічує такі рейси проєкту 2025.
- `blockId` = `<маршрут>-g<графік>`; id = `<маршрут>-<1 туди | 2 назад><NN>` за часом.
- `arrivalTime` — коли час у дорозі за радою відрізняється від суми сегментів більш ніж на 3 хв.

## Що знайшли

- OSM має 105 названих точок у межах Коростеня і маршрути №1, 7, 8 з платформами по порядку (основний API OSM,
  `relation/<id>/full.json`). Порядок зупинок №1 і №8 збігся з проєктом 2025; у №7 назад різниться петля біля
  вокзалу (ринок / вокзал).
- «Сади» в OSM — інше місце на північному заході; сезонна кінцева №8 — «Колективні сади» на півдні (підказка).
  «вул. Незалежності» в OSM стоїть там, де в раді «Вул. 1-го травня» (перейменування?).
- Дві малинські заглушки на сайті ламали Коростень і виправлені (для Малина без змін):
  `datasetToLocalViewModel` завжди брав центр карти Малина → тепер центр із профілю міста; список «перевірених»
  маршрутів Малина (`VERIFIED_ROUTE_IDS`) давав маршрутам Коростеня з іншими номерами по 2 хв на перегін і ховав їхні
  лінії → `isVerifiedRoute` / `verifiedRouteIds()` вважають усі маршрути іншого міста перевіреними
  (`setVerifiedRoutesCity`, перемикає `useTransportDataset`).

- Google (2026-11-12): Routes TRANSIT знає лінії 1–8 і 2Б Коростеня. Places знайшов 78 із 83 зупинок, але частина —
  однойменні зупинки в інших місцях (ДУ, Дитсадок №2, Проліскова, Діагностичний центр — за 4–7 км). У локальній версії
  з Google: OSM — 43, Google — 24, середина вулиці — 11, між сусідами — 4, продовження лінії — 1.
