## Этап 1. Деньги и защита от фрода (P0)

### 1.1 Награда не должна попадать в выплаты до модерации фото

**P0 · ~3ч · backend**

Сейчас `createRewardIfNotExists` создаёт запись со статусом `pending`, а `buildPayoutBalancesFromRewards` считает `pending` и `approved` как «к выплате». Итог: сумма висит в очереди с активной кнопкой «Виплатив» ещё до того, как кто-то открыл фото.

- [x] Ввести статус `hold` — начальный для всех новых наград (`referral.ts:478`)
- [x] `buildPayoutBalancesFromRewards`: в `payableUah` считать **только** `approved` (`referral.ts:907`)
- [x] Ставить `approved` только из ручного апрува заявки (`PATCH /admin/referrals/proofs/:id`)
- [x] Мигрировать существующие `pending`: если фото заявки не `approved` → `hold`
- [x] Обновить `getReferralStatsForPerson`: в боте показывать «на перевірці» и «до виплати» раздельно
- [x] Обновить тесты `referral.test.ts` под новый статус

> **Решено:** `hold` добавлен как новый стартовый статус, `pending` остаётся понимаемым при чтении как «на проверке» (legacy). Миграция `20260805103000_referral_reward_hold_status` разложила старые записи: с одобренным фото → `approved`, остальные → `hold`.

Обход: пригласить свой второй номер по контакту → отправить этот номер текстом в том же боте → создаётся новый Person с тем же `telegramChatId` и цепляется реферер. Побочно ломается `getPersonByTelegram` (findFirst без сортировки — бот начинает путать, кто «вы»).

- [x] В `linkReferralOnRegistration` отклонять связь, если у реферера и приглашённого совпадает `telegramChatId` или `telegramUserId`
- [x] Такую же проверку в `createReferralInvite` (по найденному Person)
- [x] Логировать попытку в админ-чат — это сигнал фрода, а не просто ошибка. Пометить все его не выплаченные бонусы на холд с этой причиной. И в админке учти этот момент. Как обрабатывать
- [x] Разовый скрипт: найти уже существующие пары Person с общим `telegramChatId`, отчёт в консоль
- [x] Тест на оба сценария

> **Отступление от формулировки:** заморозка сделана через `flagged` с защищённой причиной `SELF_REFERRAL_FLAG_REASON`, а не через `hold`. Причина техническая: `hold` снимается автоматически при одобрении фото (`findUnlockableFlaggedRewardIds`), то есть мошеннические деньги разморозились бы сами. Защищённый флаг снимает только админ вручную.
>
> **Как обрабатывать в админке:** приглашение помечается статусом `blocked_self_referral`, связь не создаётся, все невыплаченные награды обоих Person замораживаются. В админ-чат приходит уведомление. Во вкладке «Реферали» → «Підозрілі нагороди» появляется красный баннер с суммой, строки подсвечены, показан телефон «друга» для сверки, а кнопка «Схвалити» требует подтверждения в диалоге.
>
> Аудит старых записей: `npm run find-self-referrals` (только отчёт, ничего не меняет).

### 1.3 Уникальный индекс на награду

**P0 · ~1ч · backend + миграция**

`createRewardIfNotExists` делает «прочитал → создал» без constraint. Реальный триггер — отправка двух фото альбомом: два апдейта приходят почти одновременно.

- [x] `@@unique([referrerId, referredPersonId, rewardType, rideProofId])` в `ReferralReward`
- [x] Перед миграцией — проверка и чистка существующих дублей
- [x] Обернуть `create` в try/catch на P2002 → вернуть `created: false`

> Индекс назван явно (`map: "ReferralReward_dedupe_key"`), иначе автоимя Prisma вылезло бы за лимит Postgres в 63 символа. Дедупликация в миграции оставляет самую «продвинутую» по статусу запись: `paid` → `approved` → `hold` → остальное.

### 1.4 Защита выплаты от двойной отметки

- [x] Завернуть в `$transaction`
- [x] Оставить фильтр по статусу в самом `updateMany`
- [x] Возвращать реально обновлённое количество, а не длину прочитанного списка

### 1.5 Потолок расходов

**P1 · ~2ч · backend**

Сейчас ограничение только одно — 3 поездки на одного приглашённого. Ни месячного лимита на человека, ни общего бюджета, ни рейт-лимита на `/confirmride`.

- [x] Лимит суммы на получателя в месяц (Пока просто в админке показывать когда клиент может превысить 200 грн общей выплаты Выплачено + план на выплату)
- [x] Общий бюджетный стоп акции: при достижении — новые награды создаются в `hold` с пометкой - общий лимит 4000 грн (в админке явно сделать редактирование этого параметра (в базу занесем))
- [x] Рейт-лимит на `/confirmride`: не чаще N заявок в сутки на Person (не больше 2 заявок)
- [x] Уведомление в админ-чат при достижении любого из лимитов

> **Порог на человека** — только предупреждение, ничего не блокирует: строка в очереди выплат подсвечивается жёлтым с подписью «усього N грн — перевірте». Считается `виплачено + до виплати + на перевірці`.
>
> **Бюджет** хранится в новой таблице `ReferralProgramSettings` (одна строка, дефолт 4000 грн), редактируется во вкладке «Реферали». Награды сверх бюджета создаются со статусом `hold` и защищённой пометкой `REFERRAL_BUDGET_HOLD_REASON` — одобрение фото их не выпускает. При повышении бюджета те, что укладываются, автоматически снимаются с удержания и возвращаются в обычную очередь модерации.
>
> **Рейт-лимит** — 2 заявки в сутки на Person, считается по `RideCompletionProof.createdAt`. Повторная отправка фото по уже отклонённой заявке лимит не тратит.
>
> **Уведомления:** исчерпание бюджета и переход человека через 200 грн уходят в админ-чат вместе с карточкой подтверждения поездки. Срабатывание рейт-лимита в чат не шлётся (это была бы рассылка на каждый лишний тык) — если нужно, добавим отдельно.

- [x] Вынести вызов из-под условия
