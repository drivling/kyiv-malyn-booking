# «Джура» — персональний секретар. Roadmap

**Status:** фаза 0 у розробці (PR від 2026-09-25)
**Created:** 2026-09-25
**Scope:** особистий Telegram-акаунт власника → читання обраних чатів у власну базу → далі
дайджести, нагадування й чернетки відповідей. Це не бот для користувачів сайту, а інструмент
одної людини; дані не покидають БД проєкту.

Назва: **Джура** — козацький зброєносець-помічник, який носив листи й стежив за справами
старшини. Коротко, українське, унікальне серед IT-назв.

## Принципи (діють у всіх фазах)

1. **Один акаунт, одна сесія.** Уся робота з Telegram — через Telethon-сесію власника, і тільки
   всередині процесу `lunch.listener` (`backend/telegram-user/`). Друга паралельна сесія з того ж
   `.session` не працює, окремих процесів не заводимо.
2. **Читаємо, але не «читаємо».** Отримання апдейтів через MTProto не ставить «прочитано» — це
   окремий явний виклик `messages.readHistory`. Джура ніколи не викликає
   `send_read_acknowledge`/`mark_read`, не вмикає «друкує…» і не змінює online-статус. Колеги не
   бачать, що повідомлення прочитане програмою.
3. **Нічого не пишемо у джерело.** У захоплений чат Джура не відповідає. Єдиний вихід у Telegram —
   існуюча черга `LunchOutboundMessage` (`target='saved'` → «Обране» власника). Це серіалізує
   надсилання, дає ретраї/аудит і не плодить нових сесій.
4. **Дані — у своїй БД.** Prisma-моделі `Dzhura*` у спільному Postgres. Ніяких сторонніх сервісів
   у фазі 0. Телефон автора зберігається лише коли Telegram сам його віддає (контакт / приватність).
5. **Конфіг — у базі, не в env.** Які чати читати і що дублювати — галочки в `/admin/dzhura`;
   слухач перечитує їх кожні 5 с. Вимкнути все — `DZHURA_ENABLED=0`.

## Оцінка вихідного плану і ризики

План власника («читати групи через ту ж бібліотеку, писати все в універсальну таблицю, через
чергу дублювати в Обране, в адмінці — галочки, дата останнього повідомлення, JSON-експорт за
період») архітектурно правильний: один процес, один акаунт, черга як єдиний вихід, дані у себе.
Що варто знати:

| Ризик | Що робимо у фазі 0 |
|-------|--------------------|
| Авторів реакцій Telegram віддає неповно: `recent_reactions` — лише ~3 останніх, у приватних чатах його нема, у великих групах — тільки лічильники | Лічильники зберігаємо завжди точно (`reactionsJson`); авторів — коли Telegram їх дає; у приватному чаті виводимо (`chosen_order` → я, інакше співрозмовник); інакше «Хтось поставив ❤️» |
| Flood-ліміти при довантаженні історії | Telethon сам чекає `FloodWait` до 5 хв; далі задача спить і продовжує з `min_id` |
| Ліміти надсилання в «Обране» у гарячий час | Черга серіалізує; пауза 0.7 с між дублями |
| Пауза слухача під ексклюзивну userbot-сесію (`withTelegramUserSessionExclusive`) — дірка в захваті | Gap-fill при старті по `lastCapturedTgMessageId` (не `catch_up=True`, який повторно прогнав би лунч-обробник) |
| Видалення у приватних чатах і basic-групах приходить без chat_id | Позначаємо `deletedAt` лише при однозначному збігу `tgMessageId` |
| Сесія `.session` лежить у репо | Існуючий факт, поза обсягом фази 0 |
| Особисті чати | Ті ж таблиці й API (`kind=private`, `?kind=all`), UI — фаза 1 |

## Фаза 0 — «слухати і записувати» (цей PR)

**Мета:** обрані групи → повна переписка + реакції в базі → дубль у «Обране» → адмін-сторінка.

Зроблено:
- **Дані.** `DzhuraChat` (галочки `captureEnabled`/`relayToSaved`, `lastMessageAt`,
  `lastCapturedTgMessageId`), `DzhuraPerson` (ім'я, нік, телефон якщо є, `isMe`), `DzhuraMessage`
  (текст, тип медіа, reply/forward/topic, edit-історія, `reactionsJson`, `deletedAt`, `rawJson`,
  `source live|backfill`), `DzhuraReaction` (емодзі, автор або null, `addedAt/removedAt`),
  `DzhuraJob` (`sync_dialogs`, `backfill`), `DzhuraState` (heartbeat). `LunchOutboundMessage.target`.
- **Python (`telegram-user/dzhura/`).** Обробники `NewMessage`/`MessageEdited`/`Raw(UpdateMessageReactions)`/
  `MessageDeleted` → черга → один writer; `sync_dialogs` при старті й кожні 15 хв; gap-fill; backfill
  за доби Києва; heartbeat кожні 30 с. Реєструється **до** лунч-обробника, щоб захват групи обідів не
  чекав на OCR. `SIGTERM` тепер закриває пул і сесію коректно.
- **Node.** `GET /admin/dzhura/status|chats|jobs`, `PATCH /admin/dzhura/chats/:id`,
  `POST /admin/dzhura/jobs`, `GET /admin/dzhura/chats/:id/export?from&to` (JSON-файл, BigInt як рядки,
  ліміт 50 000 повідомлень). Група обідів — `captureEnabled` заблоковано у `true`, `relayToSaved` за
  замовчуванням `false`.
- **UI `/admin/dzhura`.** Статус слухача, «Оновити список чатів», таблиця груп із галочками,
  датою останнього повідомлення й лічильником збережених; «Історія…» → дати від/до → «Вигрузити JSON»
  і «Довантажити з Telegram» з прогресом задачі.
- **Формат дубля в «Обране»** (HTML): `<b>Чат</b> · Ім'я (@нік, клікабельно) · #id`, текст,
  `↩︎ у відповідь на: «…»`; медіа — `[фото] підпис`, `[файл: x.pdf]`; реакція — `Ім'я: реакція ❤️ на
  ваше повідомлення «…»`.

Обмеження фази 0 (свідомо): лише текст (медіа не пересилаються); автори реакцій — best effort;
backfill не знає авторів реакцій там, де Telegram їх не віддає; ретраїв для `failed` рядків черги
немає; особисті чати не показуються в UI.

Перевірка: `Docs/dzhura-phase-0-smoke.md`; автотести — `Docs/TESTING.md` (P0, Out of CI).

## Фаза 1 — особисті чати і перегляд

- Особисті чати в UI (фільтр «Показати особисті», API вже підтримує `?kind=all`), той самий формат дубля.
- Перегляд збережених повідомлень в адмінці (останні N, пошук по тексту/автору, фільтр за датою) —
  без експорту.
- Ретраї для `failed` рядків `LunchOutboundMessage` (експоненційна пауза), лічильник помилок на сторінці.
- Медіа: зберігати `file_id`/розмір, опційно завантажувати фото/документи у сховище.

## Фаза 2 — розуміння

- Дайджест за день/тиждень по чату (LLM): що вирішили, що завісло, хто кого чекає.
- Теги повідомлень: «потребує моєї відповіді», «дедлайн», «питання до мене» — і окремий дубль
  в «Обране» лише для таких.
- Пошук по всій історії (повнотекстовий індекс Postgres).

## Фаза 3 — дії з підтвердженням

- Нагадування («ви не відповіли Кості 2 дні») у «Обране».
- Чернетки відповідей на підтвердження власника; лише після явного «відправити» — і тільки тоді
  свідомий `mark_read` перед відповіддю, щоб поведінка виглядала природно (виняток із принципу 2,
  який вмикається вручну і поштучно).
- Календар: витягування домовленостей про час у події.

## Фаза 4 — інші канали

- Viber, e-mail як джерела в ті ж таблиці (`DzhuraChat.kind`), голосові → текст.

## Backlog / відкладене

- Ретеншн і видалення даних за запитом (зберігаємо переписку колег — потрібна політика).
- Видалення повідомлень у приватних чатах без однозначного збігу.
- Виніс `.session` із репо у секрет Railway.
- Окремий healthcheck-ендпоінт слухача замість heartbeat у БД.
