# «Джура» · фаза 0 — читання обраних чатів у базу

Python-частина персонального секретаря. Живе **всередині процесу `lunch.listener`**
(одна Telethon-сесія на акаунт — друга паралельна сесія з того ж `.session` не працює).
Roadmap і принципи: `Docs/dzhura-roadmap.md`. Ручний чекліст: `Docs/dzhura-phase-0-smoke.md`.

## Що робить

- `capture.py` — обробники Telethon (`NewMessage`, `MessageEdited`, `Raw(UpdateMessageReactions)`,
  `MessageDeleted`) → `asyncio.Queue` → один writer пише в `DzhuraChat/Person/Message/Reaction`.
  Для чатів із `relayToSaved` ставить HTML-дубль у чергу `LunchOutboundMessage` (`target='saved'`),
  який `outbound_loop` слухача надсилає в «Обране» власника (`send_message('me', …)`).
- `jobs.py` — `sync_dialogs` (список груп/супергруп/особистих із `iter_dialogs`, канали й боти
  пропускаються), `gap_fill` після старту (по `lastCapturedTgMessageId`), `backfill` за період дат
  (доби Києва) із прогресом у `DzhuraJob`.
- `relay.py` — чисте форматування (без telethon/asyncpg), покрите `test_relay.py`.
- `db.py` — asyncpg на спільному пулі `LunchDB`; усі datetime — naive UTC; JSONB через `json.dumps`.
- `autoreply.py` + `responder.py` — автовідповідь в особистих чатах (нижче).

Конфіг чатів (галочки «Читати» / «В Обране») — у таблиці `DzhuraChat`, редагується в адмінці
`/admin/dzhura`; слухач перечитує його кожні 5 с.

Черга `LunchOutboundMessage` (обидва target) ретраїться: помилка → `attempts+1`, `nextAttemptAt`
через 30 с → 60 с → 2 хв → 4 хв → 8 хв (макс. 10 хв), після 5 спроб → `failed`; `FloodWait` чекає рівно
стільки, скільки просить Telegram (до 10 спроб). Невдалі дублі повертає в чергу кнопка
«Повторити невдалі» в адмінці.

## Автовідповідь (експеримент, 2026-11-10)

Третя галочка в `/admin/dzhura` — лише для **особистих** чатів із «Читати». Поруч — скільки секунд чекати
(`DzhuraChat.autoReplyDelaySec`, за замовчуванням 80; 5…3600) і в панелі «Автовідповідь…» — необов'язкова підказка
про чат (`autoReplyNote`: хто це, тон, чого не обіцяти).

1. Співрозмовник написав → `responder.py` заводить таймер від його **останнього** повідомлення.
2. Власник відповів сам раніше (з будь-якого пристрою) → таймер скасовано. Його репліка лягає в базу і стає
   прикладом стилю — окремого «навчання» немає.
3. Не відповів → `autoreply.generate_reply` дає Claude останні 120 повідомлень чату (контекст і манера власника
   саме з цією людиною), підказку й київський час. Модель повертає 1–3 короткі повідомлення мовою власника або
   `skip`.
4. Перед надсиланням ще раз перевіряємо, що власник не відповів, поки модель думала; тоді — «прочитано»,
   «друкує…» (довжина залежить від тексту) і повідомлення. Вони зберігаються з `DzhuraMessage.isAutoReply`
   (у листуванні для моделі — «Я (авто)», у перегляді адмінки — «🤖 Джура за вас»).
5. У «Обране» йде звіт: на що і що відповіла Джура, або чому промовчала.

Модель мовчить (`skip`), коли відповідь не потрібна, коли останні повідомлення — лише медіа, коли тема серйозна,
і коли співрозмовник прямо питає, чи це людина: вона не каже, що вона людина, і не розкриває себе — відповідає
власник. У промпті заборонено вигадувати факти, обіцяти гроші, зустрічі й терміни, надсилати чутливі дані.
Повідомлення лише з фото/голосовим до моделі не доходять взагалі.

Кнопка «Що відповіла б зараз?» (`DzhuraJob` типу `autoreply_preview`) ставить той самий запит, але результат
показує лише в адмінці: у чат нічого не йде, «прочитано» не ставиться.

Запобіжники: лише `kind = 'private'`; повідомлення, старші за 3 хв (перепідключення), таймер не запускають; не більше
`DZHURA_AUTOREPLY_DAILY_CAP` автовідповідей на чат за київську добу; репліка власника посеред серії зупиняє решту;
таймери живуть у пам'яті — рестарт слухача їх просто втрачає. Кожна відповідь = один запит до Claude з листуванням
чату (текст іде в Anthropic API).

## Гарантії

- Ніколи не викликаємо `send_read_acknowledge` / `mark_read`: у колег не з'являється «прочитано».
- Ніколи не викликаємо `SetTypingRequest` / `UpdateStatusRequest`.
- Нічого не пишемо у захоплені чати; єдиний вихід у Telegram — черга `LunchOutboundMessage`.
- **Виняток з усіх трьох** — особистий чат, де власник сам поставив «Автовідповідь», і лише в момент такої
  відповіді (`responder.py`): без «прочитано» відповідь на непрочитане повідомлення видала б програму.
- Власні вихідні повідомлення зберігаються, але в «Обране» не дублюються; Saved Messages
  (`chat_id == me.id`) не читаються взагалі.

## Змінні середовища

| Змінна | Опис |
|--------|------|
| `DZHURA_ENABLED` | `1` (default) — підключати Джуру до слухача; `0` — лунч працює як раніше |
| `ANTHROPIC_API_KEY`, `ANTHROPIC_WORKSPACE_ID` | ті самі, що для OCR меню; без ключа автовідповідь вимкнена (адмінка попереджає) |
| `DZHURA_AUTOREPLY_ENABLED` | `1` (default); `0` — вимкнути автовідповідь усюди, хоч би які галочки стояли |
| `DZHURA_AUTOREPLY_MODEL` | лише `claude-*`; за замовч. `claude-opus-5-5` |
| `DZHURA_AUTOREPLY_DAILY_CAP` | скільки автовідповідей на один чат за київську добу; за замовч. `40` |

Решта — ті самі, що в `lunch/README.md` (`DATABASE_URL`, `TELEGRAM_API_ID/HASH`, сесія).

`DzhuraPerson.accessHash` (Telethon `User.access_hash`) зберігається разом із автором: за ним `send_message.py --user-id`
пише авторам оголошень без username і номера (кеш сесії на Railway зникає при деплої). Джура сама нічого не пише —
відправляє юзербот у бекенді, з добовим лімітом (`TELEGRAM_USER_DM_BY_ID*`).

## Логи

`[dzhura] attached me=… lunch_group=…`, `[dzhura] watching N chat(s): …`, `[dzhura] dialogs synced: …`,
`[dzhura] job backfill id=… params=…`, `[lunch] outbound sent id=… target=saved`.
Автовідповідь: `[dzhura] attached … autoreply=on|off`, `[dzhura] autoreply chat=<id> надіслано 2 з 2`,
`… власник відповів сам — таймер скасовано`, `… модель вирішила промовчати`, `… денний ліміт …` — без текстів
повідомлень (вони лише в базі й у звіті в «Обране»).
