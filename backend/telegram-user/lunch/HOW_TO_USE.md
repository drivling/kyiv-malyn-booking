# Як користуватись обідами (група + адмінка)

Група: **Обіди для НЕ бідних**. Бот = ваш особистий Telegram-акаунт (Telethon listener на backend).

## Що має крутитись

Після деплою backend у логах Railway має бути:

```
[lunch-listener] starting python -m lunch.listener
[lunch] listening group=Обіди для НЕ бідних ...
```

Без цього команди в чаті **не відповідають**. Перевірте `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, файл сесії, `DATABASE_URL`, `LUNCH_LISTENER_ENABLED` не `0`.

## Щоденний сценарій

1. **Меню**  
   - Фото в групу (OCR, якщо є `OPENAI_API_KEY`), **або**  
   - ChatGPT + JSON → адмінка `/admin` → **Столова** → «Зберегти меню» (галочка «в групу»).

2. **Замовлення** — люди пишуть у чат страви (`Пюре | Котлети` або через кому).  
   Listener відповідає сумою. Якщо текст **не** зіставлено з меню — мовчить (чат/меми).  
   Якщо день уже закритий і текст **розпізнано** як заказ — «Прийом замовлень закрито.»

Фото в чат без `OPENAI_API_KEY` listener **ігнорує** (без спаму «OCR вимкнено»). Меню тоді лише через адмінку.

3. **Оплата** — `оплатив 150` / `Оплата 175` / `!pay 150` у чаті, **або** в адмінці кнопка **Оплатив**.

4. **Підсумок Святослава** (цитати `> Імʼя:`) — закриває прийом замовлень.

5. **Ітог у групу** (адмінка) — пост «імʼя: страви — N грн» без судочків.

6. Якщо загубилась **одна людина** — у адмінці панель **«Писали в групі сьогодні · без замовлення»**
   (список із «Джури», Telegram не чіпається) → **Розібрати**: знаходить повідомлення цієї людини за день
   і розбирає лише її (чужі замовлення, ручні правки й ручні оплати лишаються). Те саме — кнопка
   «Розібрати» в рядку замовлення. Якщо страви не збіглись з меню, людина з'являється **порожнім рядком**
   з її текстом: «Редагувати» → вибрати страви (або «Прибрати»). Після розбору показується звіт: що
   сталося з кожним повідомленням і чому пропущено.
7. Якщо зламалось усе — **Розібрати поточний день**: скидає ВСІ замовлення й оплати (і ручні правки) та
   читає чат заново; у звіті видно, які повідомлення пропущено і чому.

## Команди в групі (від будь-кого / від вас)

Пишіть **точно з `!` на початку** (працюють і ваші власні повідомлення):

| Команда | Що робить |
|---------|-----------|
| `!зведення` / `!summary` / `!сводка` | хто що взяв, суми, борги |
| `!борги` / `!debts` | хто скільки винен |
| `!меню` / `!menu` | меню на сьогодні |
| `!закрити` / `!close` | закрити прийом (оператор) |
| `!відкрити` / `!open` | відкрити день (оператор) |
| `!pay 150` | оплата 150 грн |
| `оплатив 150` / `Оплата 175` | те саме без `!` |

Картка (16 цифр) у чаті зберігається на день.

## Адмінка `/admin` → вкладка «Столова»

- Вставити JSON меню → зберегти (± пост у групу)  
- Відкрити / Закрити день  
- Повторити пост меню  
- **Розібрати поточний день**  
- **Ітог у групу**  
- **Оплатив** навпроти боржника  

## Як розпізнаються страви

- Слово-категорія («салат», «суп») саме по собі не є збігом: «салат оливʼє» ≠ «Салат грецький».
- Якщо підходить кілька страв майже однаково («салат» при трьох салатах, «філе курки» при двох філе) —
  слухач **не вгадує**: частина лишається нерозпізнаною, а у відповіді в групі питає «це А чи Б?».
- Синоніми **не додаються автоматично**. Їх додає людина: поле «як писала людина» при правці замовлення
  або картка страви в «Базі страв». Один текст = одна страва; якщо той самий текст лежить на двох
  стравах, у «Базі страв» він підсвічений червоним (діє найновіший — зайвий видаліть).
- Точна канонічна назва страви сильніша за синонім іншої страви.
- **Кількість** у тексті враховується: «2 хліба», «хліб 2», «Хліб 4 шт», «Голубці ліниві 2 порції», «х2 пюре»,
  «котлети ×2». Номер пункту списку («3.гречка») — не кількість.
- «гречка **і** філе курки», «пюре **+** котлети», подвійний пробіл — це дві страви, лише якщо кожен шматок окремо —
  інша страва з меню. «Вареники з картоплею і цибулею» лишається варениками (цибуля — частина іншої назви).
- Текст без роздільників («Печінка смажена салат капуста огірок деруни») ділиться за меню, якщо кожен шматок
  впевнено й повністю збігається з окремою стравою; інакше — не вгадуємо.
- Частини-заперечення не записуються: «Дерунов нету», «Небуде 1 голубців», «Крабовий закінчився», «Замість пюре, …»,
  «Немає зеленого борща», «хліба не треба». Посилання (чек monobank) і @згадки не звітуються як «не розпізнав».
- Короткий синонім не «зʼїдає» довший текст: синонім «філе» (риба) не робить «філе курки з помідором» рибою; і
  інший варіант страви не підставляється («філе курки з помідором» ≠ «Філе курки «Пікантне»») — бот перепитає.

## Дозбір (самолікування)

Слухач перезапускається, коли backend займає Telethon-сесію (пошук телефону, розсилки) — на ці секунди
наживо повідомлення не ловляться. Тому при кожному старті й коли в адмінці змінили меню на сьогодні
слухач сам **дозбирає** останні 3 години: створює замовлення лише тим, у кого його ще немає (скасовані
через «Прибрати» не воскрешає), додає оплати без дублів і підтверджує людині у групі.

Те саме для замовлень, зроблених **до завантаження меню**: якщо в замовленні лишилось «не розпізнано» або
страва, якої сьогодні немає, його розбирають ще раз за сьогоднішнім меню. Текст пояснюється повністю — рядки
замінюються; частково — лише додаються знайдені страви; нічого нового — замовлення не чіпається. Ручну
кількість лотків зберігає, а нашу відповідь у групі **править** (edit), нову не пише.

## Власні страви оператора в нумерованому підсумку

Якщо оператор збирає замовлення списком «1. … 2. … 3. …» і свої страви пише лише в цей список (окремого
повідомлення немає), система їх бачить так: після звірки списку з повідомленнями людей лишається **рівно
один** пункт, якого ніхто не писав, — це замовлення автора підсумку. Спрацьовує в «Розібрати день» і в
дозборі (старт слухача / зміна меню), не наживо — підсумок правлять протягом дня.

Запобіжники (краще нічого не приписати, ніж приписати чуже): пункт має повністю розпізнатись за меню й мати
не більше 5 різних страв (і не більше 10 порцій); у автора ще немає замовлення (навіть скасованого); пояснено не менше 60% пунктів; серед
повідомлень людей немає невикористаного зі спільною стравою (тоді це схоже на змінене замовлення). Інакше
у звіті розбору буде рядок «[підсумок списком]» з причиною, і замовлення додається вручну.

## Перевірка розпізнавання на реальній історії («золоті дані»)

Архітектура одним абзацом: каталог страв `LunchDish` (+ синоніми) → на кожен день `LunchDay` з меню
`LunchMenuItem` → замовлення `LunchOrder` (оригінальний текст `rawText` + підсумкові рядки `LunchOrderLine`),
оплати `LunchPayment`. Повідомлення групи окремо зберігає «Джура» (`DzhuraMessage`, з 25.09).

Золотом є лише те, що перевірила людина. Підтвердження бота в групі НЕ золото: бот помилявся (напр.
«салат грецький» → «Овочевий мікс») і ніхто не виправляв. Тому беремо підсумкові рядки замовлень з БД:

```bash
curl -H "Authorization: $ADMIN_TOKEN" "$API/admin/lunch/history?from=2026-09-01&to=2026-10-02" > history.json
cd backend/telegram-user
python3 -m lunch.golden_from_history history.json lunch/golden/history.jsonl   # gold = замовлення міняли після створення
python3 -m lunch.golden_eval lunch/golden/history.jsonl --baseline e73f2c5     # новий матчер проти старого
```

`gold` — правка адміна; решта — «срібло» (автоматичний результат), розбіжності з ним — список для перегляду,
а не вирок. Не коміть вигрузку історії в репозиторій: там реальні тексти замовлень людей.

**Більший набір з «Джури».** Історія — це лише замовлення, що потрапили в БД. Повідомлення групи («Джура») додають
загублені замовлення (слухач лежав), текст до й після редагування, відповідь бота і чат, який НЕ має ставати
замовленням. Чернетка для ручної перевірки:

```bash
curl -H "Authorization: $ADMIN_TOKEN" "$API/admin/dzhura/chats/<id групи>/export?from=2026-08-01&to=2026-10-02" > dzhura.json
python3 -m lunch.golden_from_dzhura history.json dzhura.json draft.jsonl   # у полі review — що не сходиться
```

Кожен кейс чернетки переглядаєш очима: виправляєш `expected`, ставиш `"leftover": true` (частина тексту законно
не страва: чек, «віддам готівкою», страви сьогодні немає), `"expected": []` для не-замовлень і `"note"` — чому так.
Імена, чеки й @нікнейми прибираєш, лише тоді набір іде в `lunch/golden/`.

Перевірений набір `lunch/golden/2026-08-26_2026-10-02.jsonl`: 23 дні з меню, 208 кейсів (174 замовлення + 34
не-замовлення). `source`: `admin` — рядки після правки адміна, `review` — перевірено за меню дня, `corrected` —
очікування виправлене проти того, що записав бот (з поясненням у `note`). Дні без збереженого меню (11.09, 18.09,
01.10) не входять — меню, з яким тоді працював слухач, не відновити точно.

| матчер на цьому наборі | точно | кейсів з хибною стравою | чат → замовлення |
|---|---|---|---|
| до цієї зміни (f40ccc8) | 189 / 208 | 6 | 3 |
| зараз | 207 / 208 | 0 | 0 |
| зараз, без жодного синоніма (`--no-synonyms`) | 204 / 208 | 0 | 0 |

`python3 -m lunch.test_golden` тримає це як регресію: жодної хибної страви й жодного чату-замовлення, точно все,
крім відомого промаху («Салат і а пуста огірки» — автозаміна).

## Типові проблеми

| Симптом | Що перевірити |
|---------|----------------|
| `!зведення` без відповіді | listener у логах; після фіксу outgoing потрібен новий деплой |
| Усі страви на Святославі | «Розібрати поточний день» після останнього фіксу підсумку |
| Немає сум у заказах | спочатку збережіть меню з цінами |
| Пост з адмінки «в черзі» | listener має бути запущений |
| Людина написала, а замовлення немає | «Писали в групі сьогодні» → «Розібрати»; у звіті буде причина |
| Фото меню не розпізнається | на проді немає `OPENAI_API_KEY` (у логах `photo ignored (OCR off)`) — меню вставляйте JSON-ом |
| Не видно, що робив слухач | у логах Railway `[lunch] msg … пропущено — …` / `order msg=…` (вивід тепер без буфера) |
